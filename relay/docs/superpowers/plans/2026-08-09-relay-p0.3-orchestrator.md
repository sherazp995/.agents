# Relay P0.3 Orchestrator and Run Lifecycle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A message in Slack becomes a persisted run that executes through an agent loop, reports progress in its own thread, survives a crash, and stops within five seconds when told to.

**Architecture:** A thread binds to a session; a session owns runs; a run owns steps. Every state transition is persisted before any externally visible side effect, so recovery is a database read rather than a heuristic. The agent loop drives headless Claude Code with exactly one trivial capability, because this milestone proves the loop and its governance, not the capability set. All outbound chat goes through the durable outbox rather than straight to the adapter, closing the guarantee P0.2 left unwired.

**Tech Stack:** Everything from P0.1 and P0.2, plus headless Claude Code (`claude -p`) as the agent engine, per DEC-1. No new model SDK and no API key.

## No operator prerequisite. The engine is the already-authenticated CLI

**Superseded by DEC-1 in `docs/decisions/open-questions.md`.** The agent loop uses headless Claude Code (`claude -p`) on the operator's existing logged-in session, not the Agent SDK with a separate API key. Verified: `claude -p` runs with no `ANTHROPIC_API_KEY` present.

This removes the only operator blocker in this milestone. It also makes the engine consistent with FR-CODE-20, which already specified headless Claude Code for coding.

Read DEC-1 before implementing Task 6 or Task 7. It records three consequences that change what those tasks may honestly claim, most importantly that cancellation becomes termination rather than cooperative abort.

## Global Constraints

Copied verbatim from `docs/specs/2026-08-08-relay-requirements.md` v1.10 and the phase 0 roadmap.

- **AP-5:** every step is persisted before it is executed and after it completes.
- **AP-2:** all outside content is data, never instruction. Never concatenated into a system prompt.
- **AP-8:** every table carries a `workspace_id` that is NOT NULL with a foreign key to `workspaces`.
- **FR-ORC-1:** every state transition is persisted transactionally with a monotonically increasing sequence number before any externally visible side effect occurs.
- **FR-ORC-4:** a Stop instruction halts the run at the next step boundary, and aborts a long-running tool call cooperatively within five seconds.
- **FR-ORC-8:** wall-clock timeouts at step level, default 120 seconds, and run level, default 30 minutes.
- **FR-ORC-9:** identical consecutive steps beyond a threshold force a replan; beyond a second threshold the run dead-letters and reports.
- **FR-CA-3:** outbound messages are queued durably and never lost.
- **FR-CA-4:** an unmapped user cannot start work.
- **FR-SL-3:** the reply thread is the session.
- **FR-SL-6:** the final report states outcome, what was done, what changed, artifacts, cost, duration, warnings.
- **FR-RPT-5:** the agent states what it could not verify and what it assumed, rather than presenting inference as fact.
- **FR-RPT-10:** no diffs, file bodies, raw logs, or long output in any chat surface.
- **FR-SEC-1 and FR-SEC-2:** no secret in any log, error, or database column. Credentials brokered.
- **FR-OBS-1:** structured logs carry run, session, step, and principal identifiers on every line.
- **NFR-10:** the core carries no macOS-specific dependency.
- **NFR-11:** one stated purpose per module, documented interface, independent tests.
- **Rule 45:** no dash used as sentence punctuation in prose, including comments and commit messages.
- **Rule 41 and 42:** cache test output; additive diffs run their own narrow tests, the full suite runs at the gate.
- **Never `git add -A`.** Stage explicit paths. Reviewers doing revert-and-test work in their own worktree.

## Lessons this plan encodes, because they were each paid for

Eight invariants in P0.1 and P0.2 turned out to hold only by luck, and every one was caught adversarially rather than by its author. So:

- **A test count that does not move is a red flag.** Every task reports the count before and after. A guard added without the number moving is a guard with no test.
- **Prove a guard by removing it.** Every task's self-attack section requires reverting the fix and observing the failure. Reasoning is not evidence.
- **Do not overstate coverage.** A previous report claimed a security property it had not tested, and the claim was worse than the gap. State what you did not cover.
- **Run the real artifact.** A `pg` import broke the compiled binary while every unit test passed. The CLI guard exists because of it.
- **Ask when the plan is wrong.** Five implementers asked and every one found a genuine defect in my plan. Asking is expected.

### Task 1: Workspace and principal provisioning, and the fail-closed rule

**Closes PRE-3. Closes only the provisioning HALF of PRE-2**; the fail-closed suppression is Task 8's, because suppression belongs where the orchestrator decides whether to act, not in the transport. Do not mark PRE-2 closed here.

**Files:** create `src/tenancy/workspaces.ts`, `src/tenancy/principals.ts`, `src/db/migrations/0003_orchestrator.sql`, `test/tenancy/workspaces.test.ts`, `test/tenancy/principals.test.ts`. Modify `src/chat/slack/adapter.ts` to stop emitting a raw team id.

**Interfaces:**
- `resolveWorkspaceId(pool, platform: string, platformTeamId: string): Promise<string>` returning a uuid, provisioning a `workspaces` row on first sight, idempotent under concurrency.
- `resolvePrincipal(pool, workspaceId, platform, platformUserId)` keeps its existing signature and behaviour: returns null for unmapped, never throws, never auto-creates.
- `provisionPrincipal(pool, workspaceId, platform, platformUserId, displayName, roles)` explicitly creates one. Provisioning is a separate deliberate act from resolution.
- `ChatEvent.workspaceId` now carries the Relay uuid. The platform team id moves to its own field so it is not lost.

**Requirements:** AP-8, FR-CA-4, PRE-2, PRE-3.

Tests must prove: the same team id maps to the same uuid across calls; two concurrent first-sights produce one row, not two, which needs a unique constraint and an upsert rather than check-then-insert; an unmapped user still resolves to null; a provisioned principal resolves; and the adapter no longer puts a team id where a uuid belongs. That last one needs a test asserting the emitted `workspaceId` parses as a uuid, because the original defect was exactly a type that looked fine until it hit a `uuid` column.

**Self-attack:** remove the unique constraint and confirm the concurrency test fails. Revert the uuid mapping and confirm the adapter test fails.

### Task 2: Sessions, and the bound RunContext

**Closes PRE-5.**

**Files:** create `src/sessions/store.ts`, `src/sessions/context.ts`, `test/sessions/store.test.ts`, `test/sessions/context.test.ts`. The `sessions` table comes from Task 1's migration.

**Interfaces:**
- `findOrCreateSession(pool, { workspaceId, principalId, adapter, threadRef }): Promise<Session>` where `threadRef` is the stable identity of the chat thread. Idempotent: the same thread always yields the same session.
- `Session = { id, workspaceId, principalId, adapter, threadRef, state, createdAt, lastActiveAt }`.
- `archiveSession(pool, sessionId)`.
- `sessionRunContext(logger, session, runId, stepId): RunContext` producing the bound context P0.1 built and P0.2 never used.

**Requirements:** FR-SES-1, FR-SL-3, FR-OBS-1, AP-8, PRE-5.

Tests must prove: the same thread ref yields one session across concurrent calls; a different thread yields a different session; sessions are scoped by workspace so the same thread ref in two workspaces cannot collide; and the bound context carries all four identifiers on every emitted line, asserting the line count before inspecting contents.

**Self-attack:** drop the thread-ref uniqueness and confirm the concurrency test fails.

### Task 3: Restore channel thread replies as an entry point

**Closes PRE-4.**

**Files:** modify `src/chat/slack/adapter.ts` and `test/chat/slack/adapter.test.ts`.

P0.2 shipped a deliberately narrow rule: `app_mention` at a channel root, DMs always, channel thread replies ignored entirely, because recognising a Relay thread needed sessions. Sessions now exist.

**Interface:** the adapter gains an injected predicate, for example `isKnownSession(threadRef): Promise<boolean>`, defaulting to always false so the narrow behaviour remains the default and nothing changes until the orchestrator wires it.

**Requirements:** FR-SL-2, FR-SL-3, PRE-4.

Tests must prove all five cases: mention at channel root accepted; DM accepted; thread reply in a KNOWN session accepted; **thread reply in an unrelated thread still ignored**; and with the predicate absent, behaviour is exactly P0.2's. That fourth case is the one that matters, because accepting unrelated threads is the blocker P0.2's gate caught.

**Self-attack:** make the predicate return true unconditionally and confirm the unrelated-thread test fails.

### Task 4: The outbound dispatcher, wiring the outbox into production

**Closes PRE-1.**

**Files:** create `src/dispatch/outbound.ts`, `test/dispatch/outbound.test.ts`. Modify `src/chat/progress.ts` so it dispatches rather than performing directly.

`ProgressReporter` currently calls `adapter.perform` directly and nothing in production constructs `Outbox`, so FR-CA-3's zero-lost-message guarantee is unwired.

**Interface:** `OutboundDispatcher` with the same surface the reporter already uses, backed by `Outbox`. It must solve the ordering problem the reporter creates: an `edit` depends on the `ts` its `post` returned, so a post and its dependent edits cannot be drained independently. State your sequencing design explicitly.

**Requirements:** FR-CA-3, FR-SL-4, PRE-1.

Tests must prove: a post enqueued and drained by a different process instance still delivers; an edit that depends on an undelivered post is not sent before it; a crash between post and edit leaves a resumable state; the reporter still produces exactly one message across many updates; and `finish()` still lands. That last one is non-negotiable, because a dropped final state lies about the run's outcome.

**Self-attack:** break the sequencing so an edit can precede its post, and confirm a test fails.

### Task 5: The untrusted content boundary

**Closes P0.1 gate item I-2.**

**Files:** create `src/agent/untrusted.ts`, `test/agent/untrusted.test.ts`. Modify `src/chat/contract.ts`.

`ChatEvent.raw` is typed `unknown` with a comment saying it must never reach a model. A comment is not a boundary: it does not stop `${event.raw}`, `JSON.stringify(event.raw)`, or passing it to any `unknown` parameter. P0.3 introduces the agent loop, which is exactly where someone reaches for it.

**Interface:** a nominal wrapper, for example `Untrusted<T>`, that cannot be read without an explicit named unwrap whose name states the purpose, such as `unwrapForAudit`. Provide `wrapUntrusted` and a deliberately awkward-to-misuse read path. Also provide `renderForModel(value): string` which is the ONLY sanctioned way outside content reaches a prompt, and which tags provenance so the model sees it as data.

**Requirements:** AP-2, FR-RPT-10.

Tests must prove: a wrapped value cannot be interpolated into a string usefully, asserted with `@ts-expect-error` so loosening the type fails the suite; `JSON.stringify` of a wrapped value does not expose the payload; `unwrapForAudit` works and is the only escape; and `renderForModel` tags provenance. State plainly in your report what a determined caller could still do, because a boundary that claims to be absolute and is not is worse than one honestly described.

**Self-attack:** loosen the nominal type and confirm the `@ts-expect-error` assertions fail.

### Task 6: The agent loop with one capability

**No operator key. Read DEC-1 first.** The engine is headless Claude Code (`claude -p`) on the already-authenticated session, so there is no Keychain key to check and no reason to stop for one. The rule that key requirement was protecting still stands: do not mock the engine and call the task done. If the `claude` binary is absent from `PATH` or fails to return a structured result, report NEEDS_CONTEXT and stop rather than substituting a fake.

**Files:** create `src/agent/loop.ts`, `src/agent/capabilities/echo.ts`, `test/agent/loop.test.ts`.

**Interfaces:** `runAgentLoop({ ctx, task, capabilities, cancel, limits })` returning a structured result. One capability only: `echo`, which returns its input. The point is the loop, its persistence, its limits, and its governance, not the capability.

**Requirements:** FR-ORC-2 planning, FR-ORC-8 step and run timeouts, FR-ORC-9 loop protection, AP-2, AP-5, FR-SEC-2, FR-RPT-5.

Tests must prove: the loop persists a step before executing it and after completing it; a step exceeding its timeout is aborted and recorded; identical consecutive steps beyond the threshold force a replan and beyond the second threshold dead-letter with a report; the task text reaches the model as data through `renderForModel` and never as instruction; no secret reaches a prompt, a log, or a step row; and the result states what it could not verify.

The engine is a subprocess making network calls, so tests must use an injected fake for behaviour and reserve one live check that actually spawns `claude -p`. Say which tests are which. **A suite that only ever talks to a fake has not proven the loop runs.** Per DEC-1 the live check costs real money against the subscription, so keep it to a single cheap invocation and assert on the reported `total_cost_usd` rather than adding more live runs.

**Self-attack:** remove the step-level timeout, the loop-protection threshold, and the persistence-before-execute ordering in turn, confirming a test fails for each.

### Task 7: Cancellation within five seconds

**Files:** create `src/runs/cancel.ts`, `test/runs/cancel.test.ts`. Modify the loop to honour it.

**Requirements:** FR-ORC-4, and **GT-14 is this milestone's headline exit criterion.**

A Stop must halt at the next step boundary, and abort a long-running tool call cooperatively **within five seconds**. Tests must measure the elapsed time and assert the bound, not merely that cancellation eventually happened. Prove it against a capability that would otherwise run far longer, and assert the run's persisted state reflects cancellation with partial progress reported rather than discarded.

**Self-attack:** remove the cooperative abort so cancellation only takes effect at a step boundary, and confirm the timing assertion fails against a long-running capability.

### Task 8: The orchestrator and the final report

**Files:** create `src/orchestrator.ts`, `test/orchestrator.test.ts`. Modify `scripts/slack-smoke.ts` into a real end-to-end path, or add a sibling script.

Wire it: a `ChatEvent` resolves a workspace and principal, fails closed if unmapped, finds or creates a session for its thread, creates a run, builds a bound context, executes the loop, reports progress through the dispatcher into the session's thread, and posts a final report.

**Three things Task 8 must wire that earlier tasks deliberately left as defaults, each verified missing by a reviewer. The gate will check all three against real callers, not against this plan's claims.**

1. **Schedule the outbox drain.** Task 4's dispatcher only enqueues. Nothing in the process calls `drain()`, so a message survives a crash durably and then never reaches Slack. PRE-1 is not closed until a running process drains on an interval or on enqueue, with the loop surviving a failed drain rather than dying. This is the difference between a durable queue and a write-only one.
2. **Wire `isKnownSession` to the real session store.** Task 3 left it defaulting to always-false, so channel thread replies are still ignored in production. PRE-4 is not closed until this is wired and an unrelated thread is still proven ignored end to end.
3. **Suppress null-principal events.** Task 1 provisioned principals but nothing enforces that an unmapped user cannot start work. PRE-2 is not closed until this lands, allowing at most the single informational reply the spec permits.

Also add the test Task 3's reviewer asked for and could only prove by hand: a `isKnownSession` that throws, and one that is slow, must not lose the event, kill the adapter, or wedge the dedupe state. Task 8 replaces the fixed-boolean predicate with a real database query on the inbound path, which is exactly when that matters.

**Requirements:** FR-SL-3, FR-SL-6, FR-CA-4, FR-RPT-5, FR-RPT-10, FR-ORC-1.

The final report must carry outcome, what was done, what changed, cost, duration, and warnings, with **no long content in chat**. Tests must prove: an unmapped principal produces at most one informational reply and no run; a run is fully persisted before any Slack call; a second message in the same thread joins the same session; and the report contains every required field.

**Live verification, and the honest gate:** with the operator coordinating, send a real DM and confirm a run executes, progress updates in the thread, and a final report posts. **Do not claim this from a mock.**
