## Blockers

1. **No production Stop path, so GT-14 is not met end to end.** `src/orchestrator.ts:343` registers a cancellation token, but no production code calls `CancellationRegistry.cancel`. Worse, `src/chat/slack/adapter.ts:501` serialises every event behind one `#deliveryQueue`, so a Stop message would queue **behind the run it is trying to cancel**. Task 7 measured cancellation at 2ms and that measurement is real; it measured a mechanism nothing can reach from Slack.
2. **Run transitions have no monotonic sequence.** `0007_agent_runs.sql:16` states only `steps.seq` carries one, and step completion updates a row without incrementing it. FR-ORC-1 requires a monotonic sequence for the transitions it most concerns.
3. **Post durability split across two transactions.** `src/dispatch/outbound.ts:456` inserts a placeholder, then separately enqueues. A crash between them leaves a placeholder with no action text and no outbox row, permanently losing a decided message. FR-CA-3.
4. **A 60 second outage permanently fails queued messages.** `DEFAULT_MAX_ATTEMPTS = 5` with 1, 2, 4, 8 second backoff is roughly 18 seconds of patience, then terminal `failed`. Connectivity returning at 60 seconds retries nothing. Contradicts FR-CA-3 and the spec's own chaos test TST-C-4, which is a 60 second partition.
5. **A run whose only action failed or timed out reports `Outcome: succeeded`.** `src/agent/loop.ts:732` appends a warning, and line 815 unconditionally calls `finishRun(..., 'succeed', ...)`. `test/agent/loop.test.ts:622-625` explicitly pins that behaviour. Relay can tell the operator it succeeded when its only action failed.
6. **The run timeout does not bound database operations.** The timer aborts `outerSignal`, but store calls take no signal and `src/db/pool.ts:13` sets only `connectionTimeoutMillis`, no statement or lock timeout. A blocked query keeps a run alive past both deadlines. FR-ORC-8.

## High

1. **A dispatcher can claim another workspace's outbound rows.** `src/chat/outbox.ts:240` filters `status` and `adapter` only. Latent until Task 8 scheduled a production drain, which made it reachable.
2. **Parent-child workspace consistency unenforced.** `runs.workspace_id` and `runs.session_id` are independent, as are `steps.workspace_id` and `steps.run_id`, so Postgres accepts a run labelled workspace B holding a session from A.
3. **Task data and ambient credentials exposed through subprocess argv and environment.** `src/agent/loop.ts:193` puts the prompt in `args`, and `spawn` supplies no explicit `env`, so the child inherits everything. A credential pasted into Slack becomes world-readable in the process table, and unrelated shell tokens become readable by the engine. The Keychain provider was careful about exactly this; the care was not carried to a new subprocess boundary.
4. **Unexpected loop failures leave the row `running` forever** while reporting `failed` to Slack, with `test/orchestrator.test.ts:469-476` asserting the disagreement.
5. **Replies from a second principal are attributed to the session opener.** `src/sessions/context.ts:35` returns the original `principal_id` while the run is created with the current event's principal, so logs name the wrong person. FR-OBS-1.

## Medium

1. **Shutdown neither cancels nor awaits active runs.** `stop()` stops the schedulers, `SlackAdapter.stop()` does not await `#deliveryQueue`, and the script then calls `process.exit(0)`, so shutdown can cut off persistence and final reporting mid-run.

## Pattern worth naming

Three of these are the same shape the project keeps producing: a mechanism that exists, is tested in isolation, and is unreachable or unenforced in production. Cancellation is registered and uncallable. The outbox claim accepts a workspace and ignores it. Run rows say `running` while Slack says `failed`. In each case the unit test passes because it exercises the mechanism directly rather than through the path production uses.

A scoped re-review verdicted all twelve ADDRESSED, and three of its verifications went past what was asked:

## Correction: the first PASS and the first `p0.3` tag were wrong

Recorded here rather than quietly amended, because the failure is mine and the record should show it.

I declared PASS and cut `p0.3` while **two fixes sat uncommitted** in `src/chat/slack/adapter.ts`. Commit `15e6e88` claims "Medium 1, bounded shutdown" and committed the unbounded `await this.#deliveryQueue`; five later commits went past the file without picking it up. The session hook caught it, I verified both claims, deleted the tag, and had the orphaned work committed with tests.

What the tag had certified:

1. **`stop()` awaited the delivery queue with no bound**, so a hung handler wedges shutdown forever and negates the orchestrator's own `SHUTDOWN_SETTLE_TIMEOUT_MS`. Now bounded, measured at 15001 to 15003 ms against a 15 s bound; reverting it makes the new test time out at 25 s.
2. **The Stop path claimed its dedupe key before reading the handler**, so a Stop arriving with no handler burned the key and Slack's retry was silently dropped, **losing the Stop permanently**. That is a GT-14 failure in the very path the fix wave existed to create, and it is the same class of bug an earlier milestone already fixed once in a different path. Now the handler is read at line 770, the early return is at 771, and the key is claimed at 772. Reverting it fails the new test.

Root cause, mine and not the fixer's: I ran `git status --short` during earlier task verifications and **not before tagging**. My final check was `git tag` and diff totals. Across three milestones I insisted implementers never report a count they had not just measured, then certified a release without checking whether the tree was clean.

The process lesson is narrow and mechanical, so it belongs in the roadmap rather than in anyone's judgement: **verify a clean tree immediately before tagging, and confirm the fixes a verdict depends on are in `HEAD` rather than in the working tree.** Passing tests proved nothing here, because the passing code was never committed.

Final state: 394 tests, 393 passing, 1 gated live skip, typecheck clean, `relay doctor` nine checks ok, tree clean, both fixes in `HEAD` with tests and mutation checks.
